# Adding and reviewing practice

Every task needs a curriculum purpose, one defensible key, and feedback that explains a historical connection. A plausible alternative interpretation is a content bug, even when the code grades consistently.

1. Place original tasks in the appropriate chapter module or a new imported module. Use the constructors in `src/bank.js`.
2. Supply an explanation for the whole problem and a specific rationale for every selectable distractor. Do not use “incorrect” as a rationale.
3. Treat chronology as chronology and causation as causation. Do not imply every earlier event caused every later one.
4. For two-answer tasks, confirm there are exactly two defensible answers under the precise wording. Avoid using broad claims such as “political” when several economic actions also have a political meaning.
5. For order tasks, use an unambiguous temporal or logical order. Avoid simultaneous events or disputed dates.
6. Label summaries, fictional student statements, invented scenarios, and hypothetical data. Do not invent eighteenth-century voices and label them primary sources.
7. Link primary-source tasks to a transcription where possible. Keep a law’s geographic scope and exceptions visible.
8. Tag only the TEKS portion actually practiced. A grievance task does not complete the constitutional-remedy clause of 8.15(C).
9. Question identity is based on type and prompt; inserting new questions does not renumber existing records. A meaning-changing revision should receive a new identity. The test suite detects collisions.
10. Run `npm test`, `npm run build`, and `npm run audit`. Then review with an educator and actual students before claiming classroom validation.

Avoid volume inflated by reordered choices, synonym substitutions, or changed numbers without new reasoning. Maintain the finite-bank disclosure and distinguish basic retrieval from application.

Bug reports should include a task ID, disputed choice, and reasoning. Do not include names or other personal student data in public issues.
